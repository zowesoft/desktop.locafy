### DESK-DB-002 — Control-plane schema foundation

- **Repository:** desktop.locafy
- **Description:** First control-plane tables per ADR-0004: `machine` (single-row machine record), `settings` (typed key-value preferences), and `activity_logs` (engine action history, not application output). `project_settings` is deferred to the DESK-PROJ-001 migration because it needs the `projects` foreign key.
- **Dependencies:** DESK-DB-001
- **Acceptance criteria:** Machine record is a single-row upsert reflecting hostname, platform, architecture, and OS version; settings values are typed (`string`, `boolean`, `number`, `JSON`) and unique per key; activity log entries record scope, action, and timestamp; all state columns carry CHECK constraints; table access lives behind a settings/machine service module, never in UI code.
- **Status:** IN_PROGRESS
- **Assigned agent:** —
- **Files/modules:** `internal/db/migrations/`, `internal/settings/`, `internal/machine/`, `internal/activity/`
- **Tests:** Upsert/uniqueness tests; typed-value round-trip tests; activity-log append tests
- **Blockers:** — (the machine record is registered at startup and the schema is exercised by the settings, machine and activity services).
- **Evidence:** `go vet . ./internal/...` and `go test ./internal/...` pass locally on Windows and on macOS and Linux in CI (run `43585396744`), which exercises the per-platform OS version lookup on each platform: migration 0002 creates `machine` and `activity_logs` with CHECK constraints, triggers, and index; machine registration upserts exactly one row; settings round-trip string/boolean/number/JSON, reject type mismatches, and return `ErrNotFound` for missing keys; activity entries append with scope/scopeID and read back newest-first with limits; invalid scopes are rejected by the schema CHECK (test-verified).

Stopping the service kept that run's output under the row, labelled `last run`. A deliberately broken `postgresql.conf` (`bogus_setting = on`) made the start fail; the row read `Error` with `The service stopped with exit code 1. … FATAL: configuration file … contains errors` and the output panel still carried both lines after the process had exited, so the failure was diagnosable in the tab without opening the log file. Restoring the file and starting again replaced the transcript with the new run's lines.
- **Blockers:** One engine is delivered (PostgreSQL). The packaging rule itself is proposed in ADR-0020 and awaits operator approval, with the PostgreSQL slice as its evidence. The remaining engines are not delivered and none of them has been run by Locafy: ADR-0020's table was read off the vendors' published downloads, release assets and registry responses on 2026-11-23 and 2026-11-24, which shows a build exists but not that Locafy can find, initialise and supervise it. What that check found, engine by engine: MySQL publishes vendor builds on all three platforms (8.4 LTS MSI and ZIP, macOS `.dmg` and tarball, Linux tarball and Oracle repositories) and is the next candidate, still needing its own initialiser. MariaDB publishes no macOS package at all — its documentation says there is no `.pkg` and sends macOS users to Homebrew, and its 13.0.2 file listing has no macOS directory — so it fails the admission rule as published unless the operator accepts a third-party Homebrew build. Mailpit's v1.34.0 publishes static binaries for all three platforms plus Homebrew and official multi-arch images, and is the cheapest engine still to add (two ports, no initialiser). Redis has no official Windows build, and the only vendor-blessed native option, Memurai, is development-and-testing-only: its free Developer Edition shuts down every 10 days until restarted, is capped at 50% of memory and 10 client hosts, and its EULA forbids redistribution or working around that limit; ADR-0020 therefore recommends omitting Redis from the first release, with Memurai discovered but never bundled and its shutdown reported if a cache must ship in v1. MinIO's community edition publishes no binaries at all — distribution is source-only, the repository is archived, MinIO's download server now answers HTTP 410 for every community file, and the community images are gone (Docker Hub returns 404, anonymous quay pulls 401; MinIO published no dated notice of the removal) — while the maintained AIStor builds need a commercial licence, so object storage is not a native candidate and Garage or SeaweedFS are the alternatives to evaluate (PRD section 23). Shared-mode tenancy from ADR-0008 is not implemented: every instance here is isolated and owned by one project. A service is brought up by its project, but an application cannot yet declare that it needs a particular service: the ordering is project-wide (services before applications), not per-dependency. Instance output is held in memory only: the running process's recent lines, and the last run's once it exits until the next start. It is readable in the Services tab but does not survive an application restart — durable service logs with history belong to DESK-DEVX-001. macOS and Linux are compile-and-test only for this slice: the engine discovery paths and lifecycle are covered by tests and the three-platform CI jobs, not a manual run there.
- **Evidence:** The packaging rule is drafted in ADR-0020 with an engine-by-engine comparison and awaits operator approval; the PostgreSQL slice described here is its evidence. It proposes that services run as native engine processes Locafy supervises, with no container runtime required and containers only as a recorded per-engine exception; the instance keeps the ADR-0008 shape (own data directory, allocated port, own process), and only engines with a maintained native build on all three platforms enter the catalogue. `0013_services.sql` creates `services` with CHECK constraints on status and health, one live instance per name and port, a foreign key that cascades with its project, soft deletion and the `updated_at` trigger. Attaching a service allocates the engine's preferred port or the next free one (skipping ports another live instance or a listener holds), creates nothing but the row, and points the instance at `<data home>/Locafy/services/<instance id>/data` so a rename never moves it. Starting runs the engine's own initialiser once, then the server in the foreground on `127.0.0.1` with the allocated port, opening the project's database when the port first answers; stopping prefers the engine's graceful stop and falls back to the supervised tree kill; health is a TCP connection attempt on the port. Connection details are the loopback host and port, the database and role, a `postgresql://` URL and the `DATABASE_URL` line — authentication is loopback trust, so no password exists to leak. Removal stops the instance, deletes the record and keeps the data directory, which the confirmation names before it acts. The workspace overview counts attached and running services instead of showing them as planned. A project start now brings its services up before its applications and waits for each to answer before executing an application command, and a project stop stops the applications first and the services after them, so they stay up exactly as long as the project does, while a project restart cycles only the applications and leaves a running service running; both are reported in the derived lifecycle and in the activity entry (see the project-lifecycle evidence for the ordering and tests). **Verified in the running application over CDP** against the `health-smoke` project with PostgreSQL 17.2, the engine installed on this machine: the dialog reported `PostgreSQL 17.2` at its default port; attaching it produced a record on port 5433 — the machine's own PostgreSQL service holds 5432, so the preferred port was skipped — reading `Stopped` with the path `...\\Locafy\\services\\3329a3dc-5bb7-4a27-80d4-02fcebda2795\\data`; Start initialised that directory and the row became `Running · Answering`; the expanded details showed `postgresql://locafy@127.0.0.1:5433/locafy`, the `DATABASE_URL` line, host, database, user and data directory; `psql` connected as `locafy` to database `locafy` on PostgreSQL 17.2 for Windows and created a two-row table; Stop returned the row to `Stopped`; Restart came back to `Running · Answering` on the same port and directory, and the table still answered; Remove showed the warning naming the kept data directory, and confirming it emptied the list and soft-deleted the row. Running `postgres` directly on that kept directory afterwards still returned the 2 rows from `smoke_proof`, so the data survived removal, and nothing was listening on 5433 once the instance stopped.
